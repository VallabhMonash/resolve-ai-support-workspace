# AI specification

## Ownership and boundaries

The owner implements prompting, schema validation, document chunking, indexing, retrieval, source tracking, permissions, tool execution, evaluation and UI integration in TypeScript. Existing pretrained models supply inference.
Use direct provider APIs through small adapters. No LangChain, autonomous agent framework, paid API or training pipeline.

The four user-facing capabilities are:
1. Summary plus category/priority suggestion.
2. Document retrieval and a cited reply draft.
3. One model-requested read-only ticket lookup.
4. Human feedback and a reproducible evaluation report.

## Initial model profiles

| Profile | Generation | Embedding |
|---|---|---|
| Local | Ollama qwen3:4b-instruct, Q4 variant | Ollama embeddinggemma:300m, 768 dimensions |
| Hosted | Cloudflare @cf/meta/llama-3.1-8b-instruct-fp8-fast | Cloudflare @cf/baai/bge-base-en-v1.5, 768 dimensions |

These are selected starting models, not measured quality claims. M0 must prove real chat, structured output, native tool calls and embedding dimension/limits on both profiles. Record exact Ollama digests and hosted model IDs/date; hosted immutable revision may be unavailable and must be marked unavailable.
If the selected free model no longer supports a required capability, choose a free replacement with a documented reason and repeat tests. Do not silently emulate native tool calls, buy access or mark a mock as success.

Initial local generation context: 4,096 tokens, max 512 output tokens, temperature 0, one request at a time. Allow up to 120 seconds locally; hosted action deadline 75 seconds inside a Vercel handler configured for at least 90 seconds under supported Fluid Compute settings. Use an abort signal. Model token totals are tracked when supplied; missing usage is null, never zero. Temperature zero does not guarantee repeatable output.

## Adapter contract

Generation adapter accepts messages, optional JSON schema, optional tool definitions, maxOutputTokens, deadline/signal. Returns validated transport data: text or tool calls, model identifier, usage when known, finish reason. It does not choose retrieval, grant permissions or write tickets.
Embedding adapter exposes embedDocuments and embedQuery, profile metadata, maxInputTokens, dimension, and model-specific preprocessing. Validate finite numbers, vector length and nonzero norm; normalise consistently for cosine search.

Provider errors map to PROVIDER_UNAVAILABLE, AI_QUOTA_EXCEEDED, AI_TIMEOUT or MODEL_OUTPUT_INVALID. The caller never sees credentials or raw upstream responses. No automatic switch from local to cloud.

Use @huggingface/tokenizers with model-matched assets for chunking/token budgets; pin its assets/version at M0. A code-owned profile registry records preprocessing, tokenizer files, thresholds and model IDs. Package tokenizer assets from authorised public model repositories with their required notices; no runtime download on request. Do not download tokenizer assets on every Vercel request. No silent truncation by an embedding endpoint. If the runtime embedding response reports an input limit unexpectedly, split/retry the affected chunk within bounds and record the event.

## Summary and classification

Input: ticket title/description plus latest 5 comments bounded by the context budget. Earlier comments omitted with an explicit marker.
System instructions: summarise only supplied facts, distinguish customer claims, use enum categories, propose priority from a written rubric.
Output schema:
- summary: string <= 600 characters
- category: IMPORT_EXPORT | ACCESS | SYNC | OTHER
- priority: LOW | NORMAL | HIGH
- rationale: string <= 300 characters

Priority rubric: HIGH = explicitly blocked core workflow, loss of access or credible data-loss report; NORMAL = degraded functionality with workaround/unclear severity; LOW = how-to/cosmetic request with no reported block. This is a suggestion for review, not automated incident escalation.

Validate JSON with Zod. One bounded repair attempt is allowed for invalid JSON/schema if time and quota permit. Count invalid first attempts separately. Never silently coerce an unknown enum. User explicitly applies suggestions with expectedVersion.

## Document preparation and RAG

1. Create/version a plain-text or Markdown article.
2. Remove executable/raw HTML; retain headings and meaningful code/error strings as plain content.
3. Split by headings/paragraphs, then model tokens: target 256 tokens, max 320, overlap 40. Store title, version, ordinal and offsets. Include prefixes/title within the embedding model's total limit.
4. Generate embeddings with the selected profile; persist validated vectors and chunk provenance.
5. Mark job READY only when every chunk for current article version exists and is valid.
6. For a draft request, embed a bounded query from ticket title/description and relevant latest comments.
7. Search current READY chunks in the authorised workspace (or published template for demo) with the exact active profile. Retrieve top 5 by cosine similarity.
8. Keep at most 3 source passages within a 1,400-token combined evidence budget; exact token accounting includes message overhead and output reserve.
9. Pass labelled sources S1, S2, S3 and ticket context to the LLM. Ask for a grounded answer or an insufficient-evidence result.
10. Validate the output and resolve source labels through the server's retrieved map. Save immutable citation snapshots.

Initial indexing batch size: 4 chunks, one request at a time. UI or owner CLI resumes the next batch. Document embedding results are reused by content hash + profile only within authorised scope. Never mix vectors from the two model spaces.

Tune a retrieval similarity threshold on the development set separately for each profile; freeze the values before test evaluation. There is no universal cosine threshold that proves answerability. Empty retrieval returns INSUFFICIENT_EVIDENCE without generation; threshold and model abstention help but do not guarantee factuality.

Draft schema:
- outcome: ANSWER | INSUFFICIENT_EVIDENCE
- paragraphs: array of { text: string, sourceLabels: string[] }, max 5 paragraphs and 2,000 total characters
- missingInformation: string[] (max 3)
For ANSWER require at least one valid cited passage; every substantive troubleshooting paragraph must include source labels. An invalid source label rejects the result. INSUFFICIENT_EVIDENCE has no prescriptive troubleshooting answer, only a short explanation and clarifying questions.

Citations prove provenance, not truth. Manual evaluation checks whether cited evidence actually supports each claim. Do not claim the validator prevents all hallucinations. Do not use an LLM to manufacture source URLs.

## Tool calling

User action Find similar tickets starts a bounded two-generation workflow:
1. Send the ticket and ONE native tool definition: findSimilarTickets({ query: string, limit: integer 1..3 }).
2. Model requests the tool with arguments. Server validates the exact tool name, args and lengths.
3. Server injects workspaceId from session, excludes current ticket, searches RESOLVED tickets using PostgreSQL full-text search, and returns at most 3 IDs/titles/resolution excerpts.
4. Send the actual tool result back to the model for a short summary. Display only IDs that the server returned.

One tool execution and at most two generation calls; no recursive loop. If the model fails to request the required tool, return MODEL_OUTPUT_INVALID instead of presenting an ordinary search as tool calling. If there are no matches, show that explicitly.
No writes, arbitrary SQL, shell commands, network URLs, external accounts or model-controlled permissions. Ticket excerpts are untrusted data. Historical tickets are reference material, not authoritative documentation for the cited-reply feature.

## Reliability and quotas

Every AI mutation includes a client UUID idempotency key. Reserve the run and budget atomically; reuse completed output for the same key/input, return CONFLICT if key is reused with different input, and return AI_BUSY for an active duplicate. No automatic retry of the entire mutation with a new key.
Do not hold a DB transaction while waiting for a provider. Mark runs failed on errors; expired RUNNING records are reconciled as failed on next access/cleanup. Release leases in finally, with expiry set beyond the applicable action deadline plus 15 seconds as crash recovery. Recover an existing idempotent run before validating whether a new run may start against the latest ticket version.
One retry for transient provider failure (small jitter) is allowed only within the total action deadline and attempt budget. Repair and retry together may add at most one extra generation to an action. Tool action therefore max 3 generation attempts; simple classify/draft max 2. Embedding calls also consume provider attempt counters.
Quota exhaustion disables AI only; ordinary tickets remain usable unless a hosting/database quota also prevents them. No paid fallback.

## Required adversarial cases

A ticket asks to ignore instructions; an article contains fake system messages; tool args request a different workspace; a result invents a citation; a prompt tries to reveal secrets; source material does not answer the ticket; old article version is superseded; malformed JSON; provider timeout/429; duplicate clicks; cross-workspace source access. Test guards directly and evaluate real-model behaviour separately.
